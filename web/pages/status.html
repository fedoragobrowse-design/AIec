What has been exercised, where the evidence lives, and what is still unproven. AIec is self-hosted: this is a record of published verification, not a live monitor of your cluster.

Available product surfaces

  • Interactive sandboxes: bounded exec and workspace-confined file operations through the Python SDK, CLI and local MCP server.
  • Durable runs and evaluations: repository checkout, commands, validations, artifacts, cancellation and bounded comparisons.
  • Recovery: PostgreSQL leases and generation fencing, with workspace archives in S3-compatible storage. Running VM memory is not the portable recovery unit.
  • Quality gate: formatting, clippy, workspace tests, SDK documentation contracts, Python SDK tests and an aarch64 cross-build.

Known limits

The parallel soak is not a clean 80/80.

The dated run completed 77/80 with three transient no schedulable worker has capacity refusals. Resource censuses returned to baseline. Their cause remains unattributed, and the soak has not been rerun after the scheduler fix. Read the original measurement.

  • Multi-host security: separate control and worker hosts and separate gateway modes are documented, not validated by the single-host evidence.
  • aarch64: cross-build evidence only; no hardware runtime or performance claim.
  • Encrypted traffic: hostname visibility is not method or path visibility. CONNECT to a governed host requiring Layer 7 checks is refused, not forwarded ungoverned. TLS interception is not claimed as a validated deployment mode.
  • File canaries: trusted host file APIs can observe reads; arbitrary in-guest exec reads are not observable through those APIs. Guest and harness logs are contextual, not trusted enforcement evidence.
  • Storage accounting: per-request size ceilings exist; aggregate per-tenant snapshot and persistent-storage byte quotas remain absent.
  • SDK and Run listings: run_cells chunking and per-Run pagination for events, attempts and artifacts remain unimplemented.
  • Operations: no SLA or hosted service. API endpoints may change before 1.0; you own capacity, monitoring, upgrades and backups.

Before you deploy

Build and deploy the guest image, configure image trust and TLS, protect credential files, and run the watchdog. Guard workers need CAP_NET_ADMIN and CAP_NET_RAW; the packaged systemd unit grants both, and another launcher must do so explicitly. Follow the deployment guide and reproduce the relevant acceptance suites on your hosts.

For the threat boundary and vulnerability reporting, read Security. The report and known-defects record keep measured limitations separate from fixed defects.
