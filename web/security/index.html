Security

AIec runs code written by autonomous agents. That code is treated as hostile, and the isolation boundary is the product.

The boundary

tenant A sandbox  ─┐
                   ├─ microVM: own kernel, own filesystem, own netns
tenant B sandbox  ─┘
                        │
                        ├─ vsock control channel (never on the network)
                        └─ egress filtered by nftables policy

Firecracker, always, for untrusted code

Public workloads run in microVMs with their own guest kernel. A tenant cannot request a weaker runtime and downgrade their own isolation. Docker remains available only for trusted self-hosted deployments and local development.

Nothing shared

Each sandbox gets its own kernel, root filesystem and network namespace. A bug in one guest does not reach another guest, and the host kernel is not exposed to the workload at all.

Deny-all by default

A sandbox reaches exactly one path, its own gateway. The host LAN, RFC1918 ranges, link-local and cloud metadata addresses, the control plane, worker management endpoints, other tenants, all IPv6 and all forwarding are dropped, with no NAT and no accept on connection state. A sandbox that asks for a network without selecting a policy is refused rather than quietly filtered or quietly granted; the unguarded backend exists only if the operator names it.

Governance outside the guest

Guard keeps policy, the network gateway, credentials and the evidence journal on the worker rather than in the machine. A guarded sandbox reaches exactly one path, its own gateway; model traffic carries a placeholder that the gateway swaps for a real credential the guest never holds, and no policy selected means no network. Encrypted tunnels are not inspected by default, so a rule needing method or path visibility is refused unless the operator turns on interception and acknowledges that Guard will then hold a key able to read the traffic it governs.

Tenancy is enforced server-side

Every tenant-scoped query is filtered by the authenticated tenant. Possession of a sandbox ID does not grant access to it; guessing another tenant's ID returns 404, not their data.

Guard

Guard is the part of AIec that governs a sandbox from outside it. The guest may be compromised; the harness inside it may be compromised; the code it runs may be hostile. What still holds is the network and credential boundary, because the things enforcing it are not in the guest.

Nothing is trusted from inside

A guarded attachment carries no egress until an out-of-guest watchdog reports an observation it has verified. Only verified observations earn a heartbeat, and the heartbeat is what keeps the network up.

Silence is not health

If the watchdog stops reporting, the gateway and the kernel rules cut the attachment and the cut latches. The machine is not destroyed, so an operator can still pause it and take a forensic capture.

Quarantine is one path

Repeated denials request a quarantine. The control plane cuts the network, pauses the machine, captures it without resuming, records durable quarantine state, appends an authoritative event, writes an incident report and notifies. Calling it twice returns the same incident rather than acting again; only a human release reopens a held machine.

Budgets are durable

Lifetime and model request and byte ceilings live in the control plane, and every request and byte is reserved there before it is forwarded. A worker restart cannot hand a machine a fresh allowance, and an authority that cannot be reached refuses traffic rather than falling back to memory.

Agent authority, not just destinations

Where Guard can see a request it governs more than the destination: MCP method and tool names, GraphQL operation kind, name and root fields, and HTTP method and path. Anything not named is denied, and a tunnel Guard cannot read is refused rather than forwarded ungoverned.

An agent may ask; only a human may approve

A policy change arrives as a proposal. Approval is a separate capability, the verifier runs before anything is applied, and the apply itself happens on the worker that owns the rules. The release capability is separate again: the key that can cause a quarantine is not the key that undoes one.

Evidence that cannot be rewritten

Every decision is a hash-chained record outside the guest, anchored in the control plane. A guest that reports what happened is treated as advice; only what Guard observed counts.

A second reviewer that can only tighten

The optional watcher returns one of four verdicts and maps them onto actions that already exist and are all restrictive. It has no path to an allow, an approval or a release, it is off by default, and it never sees anything private chain-of-thought.

Tripwires, signed images, per-machine identity

Synthetic canaries mark a fake file, hostname or credential so touching one is caught outside the guest. Guarded workloads can require a signed image manifest with verified kernel and rootfs digests and refuse to boot without it, and each machine gets its own short-lived control identity that no other sandbox can use and no snapshot carries.

The full statements, including everything Guard does not enforce, are in docs/GUARD_THREAT_MODEL.md, with the policy format in docs/GUARD_POLICY.md and the operator guide in docs/GUARD.md.

Credentials

  • API keys are stored hashed and compared in constant time.
  • Keys are shown once, scoped, rotatable and revocable.
  • Secret values never appear in logs, metadata, snapshots, error messages or audit records.
  • Transient in-sandbox secret material is destroyed with the sandbox.

Abuse resistance

Quotas

Per-tenant limits on active sandboxes, vCPU, memory and disk, enforced at placement time under a database lock.

Rate limits

Per-tenant and per-address admission control on the public API, with 429 and a Retry-After header.

Budget ceiling

A global execution budget stops new creation rather than allowing a runaway agent to become a charge.

Reporting a vulnerability

Do not open a public issue. Email security@gobrowse.dev with what an attacker can do, how to reproduce it, the affected component and version, and any request IDs (with secrets redacted). We acknowledge within 3 business days and triage within 7.

There is no bug bounty. Our full policy, including known limitations, is in SECURITY.md.

Known limitations

We would rather list these than have you find them. The current ones, and what is not yet enforced, are in SECURITY.md and summarised on the status page.
