Docs

Run it yourself. You need a Linux host with KVM, PostgreSQL, S3-compatible storage, and a configured control plane and worker.

What you need

Compute host

A Linux machine with /dev/kvm, enough RAM and disk for the sandboxes you intend to run, and the Firecracker binary. One host is enough to start; more are a matter of running more workers.

State

PostgreSQL for metadata, scheduling and the usage ledger. S3-compatible object storage for artifacts and workspace snapshots — MinIO, or anything that speaks the S3 API.

Install

  1. Get the code. 
    git clone https://github.com/fedoragobrowse-design/AIec.git
cd AIec
  2. Build the binaries and guest image. The image builder needs Docker, an uncompressed compatible guest kernel and a private guest secret. It writes image digests; configure signed-image admission separately using the deployment guide. 
    cargo build --release -p aiec-api -p aiec-cli -p aiec-mcp
export PATH="$PWD/target/release:$PATH"
export AIEC_KERNEL=/path/to/vmlinux
export AIEC_GUEST_SECRET="$(openssl rand -hex 32)"
./scripts/build-firecracker-guest.sh
  3. Check the host. aiec doctor validates KVM, the Firecracker binary, the guest artifact and its digest, the database, object storage, networking and TLS, and tells you exactly what is missing. 
    aiec doctor
  4. Start the control plane and a worker. The systemd units in deploy/ are templates; follow the deployment guide for database, object storage, TLS, image trust and worker configuration.

Your first sandbox

Create a key against your own control plane, then use the SDK. There is no account to sign up for and no key to request from anyone.

pip install agentforge-sdk
from agentforge import AIec

af = AIec(base_url="https://your-control-plane.example", api_key="af_live_...")

box = af.sandboxes.create(image="aiec-coding:latest")
print(box.exec(["uname", "-a"])["stdout"])
box.destroy()

Set base_url to your deployed endpoint, or set AIEC_URL. The SDK falls back to http://127.0.0.1:8080 for a local control plane; there is no hosted endpoint.

Core concepts

Tenant

Every API key belongs to a tenant. A tenant owns its sandboxes, snapshots, artifacts, usage, quotas and secrets. Possession of a resource ID does not grant access to it.

Sandbox

A disposable computer. It is leased from the scheduler, accounted for while it runs, and destroyed when you are done.

API key

A bearer credential. Stored hashed, shown once, revocable, rotatable, and scoped so a key can be limited to specific operations.

Runtime

Firecracker microVMs for untrusted work. Docker exists for trusted self-hosted and local development, and the control plane refuses to hand a tenant a weaker runtime than its policy allows.

Governing what a run can reach

A run that reaches the internet is governed from outside the machine. Pick a policy template and the worker enforces it, substituting model credentials the guest never holds and recording every decision where the guest cannot rewrite it. No policy selected means no network.

# Only the model endpoint, through the Guard broker
run = af.runs.create(command=["pytest", "-q"], guard="model-only")

A Guard selection replaces network rather than sitting beside it: two descriptions of one egress would be two paths to the internet, and the wider one would be the one that applied. Encrypted tunnels do not give Guard method or path visibility. A CONNECT tunnel to a host requiring those checks is refused, not silently forwarded without governance; TLS interception is not claimed as a validated deployment mode. The four built-in templates are no_network, model_only, model_plus_allowlist and read_only_api. GUARD_POLICY.md has the selection syntax, operator boundary and verifier instructions.

What runs alongside it

  • A watchdog. One process per guarded sandbox, outside the guest. An attachment carries no egress until it reports a verified observation; if it stops reporting, the network is cut and stays cut. Run one with aiec-guard-watchdog, using a key that holds only guard:read, guard:heartbeat and guard:quarantine.
  • Durable budgets. Lifetime and model request and byte ceilings are control-plane state, reserved before traffic is forwarded, so a worker restart cannot reset them.
  • Quarantine and release. Repeated denials quarantine a machine; releasing one is a separate human capability.
  • Layer 7 rules where visible. MCP tool names, GraphQL operations and root fields, and HTTP method and path, with anything unnamed denied.
  • Policy proposals. An agent may ask for a change; only a human may approve one, and the verifier runs first.

Operating a guarded sandbox

aiec guard show <sandbox>         # policy hash, attachment, budgets, incident
aiec guard events <sandbox>       # verified journal entries
aiec guard quarantine <sandbox>   # operator-initiated
aiec guard release <sandbox>      # reopen a held machine
aiec guard proposals <sandbox>    # pending and decided
aiec guard verify policy.yaml       # compile and verify, apply nothing
aiec guard import-openshell policy.yaml --out guard.yaml

The worker needs CAP_NET_ADMIN and CAP_NET_RAW. The packaged deploy/aiec-worker.service grants both; an alternate launcher must grant them explicitly. If the nftables startup probe fails, the worker reports network_policy: false and refuses governed placement. Check the host with aiec doctor, and configure the watchdog and credential bindings before starting governed workloads.

Driving it from an agent

The local MCP server exposes the same lifecycle as tools: create a sandbox, run commands, read and write files, clone a repository, destroy it. It talks only to a control plane you run, so the workload stays on hardware you control.

Operating it

The deployment guide covers TLS, workers, object storage, backup and restore. The architecture guide explains placement and fencing; the API reference lists request and response shapes. Use the Guard report for acceptance evidence, exact reproduction commands and measured limits.

There is no cloud, no hosted API and no sign-up. Everything runs where you put it.
