Disposable virtual machines for AI agents.

AIec hands an AI agent a Firecracker microVM to work in, records what it did, and then destroys the machine. Nothing to clean up between runs — and the evidence outlives the VM.

set up everything in one line
$ curl -fsSL https://aiec.gobrowse.dev/quickstart.sh | bash

One line sets up everything: the control plane, a worker, the MCP server, and the Python SDK. A minute later an agent is running code in a disposable machine on your host. Prefer pieces? Start below.

A container gives an agent a filesystem and a process. AIec gives it a virtual machine: its own kernel, its own network namespace, its own CPU and memory, built in seconds and gone a few minutes later. The agent never holds a credential for anything it can reach, and whatever it produced is collected before the machine disappears.

Give an agent a computer it can throw away

One command: a repository, the command to run, and the tests that decide whether it worked. The repository is cloned, the task executes in an isolated machine, the diff comes back, and the machine is destroyed.

The CLI prints the settled Run record as JSON because the record is the product: it is what a reviewer reads, what a CI job archives, and what a later run is compared against. The command to execute comes after the -- separator, and --validate takes a JSON argument vector, so the work and the test that judges it are declared together.

Compare two revisions, not two opinions

The comparison that ships is an OMP comparison: the same task, the same target repository at a pinned commit, the same image and the same resources, run once against the baseline revision of an agent and once against the candidate. Each side gets its own machine, each machine is destroyed, and both Run records are kept.

A real run of that comparison, recorded in benchmarks/omp-after-2026-09-30.json. One repetition, so this is an observation rather than a distribution — and it is published because it is what was measured.

baseline v9.7.0 11.23 s5.98 s2.96 s3 / 3PROOF.md
candidate v9.8.0 18.90 s6.75 s3.13 s3 / 3PROOF.md

Both revisions passed, so this run shows a cost difference and not a regression: the candidate spent 68 % more wall time inside the agent, which the Run record states and nothing interprets. An earlier sample of the same comparison failed its judgement and that artifact is in the repository too — the passing number is not the only one on file. Comparisons are driven through the API, the CLI, or the aiec_compare_omp MCP tool.

The agent does not own the boundary

Guard enforces policy from outside the guest. The machine holds no firewall configuration it can rewrite, no credential it can read, and no DNS it controls. Policy is applied by the host: nftables for egress, a Guard broker in front of the model endpoint, and credential substitution so the guest sees a proxy token rather than the real key.

Start with nothing

No network, model-only access, a model plus an allowlist, or a read-only API policy. A governed encrypted tunnel is refused rather than forwarded without checks — if the host cannot see inside it, it does not pass it.

Approval is not the agent's to give

An agent can propose a policy change. A human approves it. The proposal, the decision and the actor are recorded, so the question "who widened this and when" has an answer.

If a worker cannot enforce policy, it says so

A runtime advertises network_policy: true only when its network backend actually reports DNS control and restricted allowlists — the capability is read from the backend rather than hardcoded. A worker that cannot promise it advertises false and refuses governed placements. It does not run them ungoverned and hope.

Read the security model or drive it from an agent through MCP — nineteen tools covering the lifecycle, exec and files, plus run, compare and agent operations.

How it fits together

Self-hosted, and staying that way

There is no sign-up

No hosted API and no account. The control plane, the workers and the sandboxes run on hardware you choose — PostgreSQL for metadata, an S3-compatible store for artifacts, your own KVM hosts. You pick the capacity, the retention and the blast radius.

It will not spill your work

When every worker is at capacity, AIec refuses the placement rather than quietly moving the workload to someone else's machines. A failed request is a smaller problem than a silent change of isolation boundary.

Bring your own agent

Python SDK, Rust client, CLI, or the local MCP server for any MCP-capable coding agent. A governed run is placed only on a worker that advertised it can enforce the policy; one that cannot refuses rather than running ungoverned.

Know what is not done

Network-enabled Firecracker, the hosted isolation provider, aarch64 and storage byte quotas are all unproven or unbuilt. The roadmap labels every capability, and limitations lists what has no evidence at all.
